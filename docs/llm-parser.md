# LLM 파서와 멀티턴 대화

← [CLAUDE.md](../CLAUDE.md) · 관련: [architecture 3절](architecture.md#3-대화-한-턴의-흐름) · [IG 엔진](ig-engine.md) · [roadmap Phase 3+](roadmap.md#phase-3-기능-고도화-암묵적-선호-추론과-추천-보정)

대화에서 LLM이 하는 일 세 가지와, 그 결과로 대화 상태를 바꾸는 대화 관리자([`handle_message`](../backend/app/services/chat.py "docid:chat.handle-turn"))를 설명한다.

| 역할 | 코드 | 호출 |
|---|---|---|
| 요청 분류기: Safety 분류, 추천 조정(제외·가격 정렬) | [`parse_message`](../backend/app/services/parser.py "docid:chat.parse-message") | 자유 입력마다, 속성 추출과 동시에 |
| 속성 추출기: 발화에서 채울 수 있는 속성 값과 사용 맥락 → 메모리 | [`extract_attributes`](../backend/app/services/extractor.py "docid:chat.extract-attributes") | 자유 입력마다, 요청 분류와 동시에 |
| 질문 작성기: 방금 알게 된 것을 결론처럼 말하고, 엔진이 고른 속성을 친구 말투로 은근히 묻기 | [`write_question`](../backend/app/services/questioner.py "docid:chat.write-question") | 질문할 때마다 |

**원칙**
- **LLM은 해석과 말하기만 한다.** 무엇을 묻고 무엇을 추천할지는 IG 엔진이 상품 데이터로 정한다. LLM은 상품 속성을 만들지 않는다.
- **LLM이 있으면 의미 판정은 LLM만 한다.** "상관없음" 같은 판정을 단어 목록으로 하지 않고, LLM이 찾지 못한 것을 규칙으로 덮어쓰지 않는다. 규칙(보기 이름 매칭)은 LLM이 없거나 실패했을 때만 쓴다.
- **질문을 미리 정해 두지 않는다.** 돌려 묻는 질문은 속성별로 적어 두지 않고, 시스템 프롬프트가 방법만 알려 준다([5절](#5-질문-작성기-친구-페르소나)).
- **추출 결과를 그대로 믿는다.** LLM에게 확신도를 받지 않는다. 뽑은 값은 사용자가 직접 말한 것과 같은 조건이다. 대신 "값이 분명히 따라 나올 때만 넣으라"고 지시하고, 알게 된 것을 대화에서 드러내 사용자가 정정할 수 있게 한다([7절](#7-해석-결과를-대화-상태에-반영)).

## 1. 입력 해석 순서

| 입력 | 처리 | LLM 호출 |
|---|---|---|
| 보기 버튼 | `answer {attribute, value}`를 그대로 반영하고 메모리에 남긴다 | 해석 없음 (질문 작성 1회) |
| 자유 입력 | 요청 분류 ∥ 속성 추출 → 메모리·선호 반영 | 2회 동시 (+ 질문 작성 1회) |
| 자유 입력 + LLM 없음(키 미설정) 또는 실패 | 대기 중인 질문의 보기 이름과 문자열 매칭([`match_text`](../backend/app/services/chat.py "sym:py:app.services.chat#match_text")). 의미 판정(상관없음 등)은 하지 않고 버튼으로 고르게 한다 | 없음 |

## 2. 파서

[`parse_message`](../backend/app/services/parser.py "docid:chat.parse-message")가 두 호출을 스레드 두 개로 동시에 보내고 결과를 하나(`ParseResult`)로 합친다. 기다리는 시간은 둘 중 느린 쪽이다.
요청 분류는 맥락에 끌려가면 안 되고(Safety), 속성 추출은 맥락을 잘 써야 해서 지시를 나눴다.

### 입력
- **시스템 지시:** 카테고리 정의(YAML)의 속성·값·라벨로 만든다. 카테고리별 코드는 없다.
  - 요청 분류기: [`build_instructions`](../backend/app/services/parser.py "docid:chat.parser-instructions")
  - 속성 추출기: [`build_instructions`](../backend/app/services/extractor.py "sym:py:app.services.extractor#build_instructions")
- **사용자 입력:** 발화와 함께 맥락([`ParseContext`](../backend/app/services/parser.py "sym:py:app.services.parser#ParseContext"))을 넘긴다.
  - 직전 질문의 실제 문장과 질문 의도(속성). 돌려 물은 질문("주로 어디서 들어?")에 대한 짧은 답을 해석하는 데 쓴다
  - 메모리 요약: 지금까지 알게 된 속성 값(근거 발화 포함)과 사용 맥락
  - 현재 추천 목록 요약(추천 후일 때, 요청 분류기만): 상품명 | 가격 | 속성들

### 출력 (구조화 출력, [`schema_for`](../backend/app/services/extractor.py "sym:py:app.services.extractor#schema_for"))

| 호출 | 필드 | 내용 |
|---|---|---|
| 요청 분류 | `request_type` | `shopping` / `other_product` / `off_topic` / `unsafe` |
| 요청 분류 | `language` | 발화의 언어 `ko` / `en`(그 밖의 언어는 `en`). 응답 언어가 된다(대화 상태 `language`) |
| 요청 분류 | `exclude_ranks[]` | "1번 말고" → 현재 추천에서 뺄 순위. 현재 추천이 없으면 버린다 |
| 요청 분류 | `price_order` | "더 싼 걸로" → `cheaper`, "더 비싸도 좋은 걸로" → `pricier`, 그 외 `none` |
| 속성 추출 | `constraints[]` | `{attribute(enum), value, quote}`. 이번 발화에서 새로 말하거나 바뀐 것만. `quote`는 근거 발화를 그대로 인용 |
| 속성 추출 | `notes[]` | 속성으로 표현되지 않는 사용 맥락("지하철 출퇴근", "안경 착용"). 사용자가 쓴 언어로 |
| 속성 추출 | `keywords[]` | 상품 설명 검색용 영어 키워드("하루 종일 껴도 편했으면" → `comfortable`, `all day wear`). 동률 정렬의 BM25 질의([IG 엔진 4절](ig-engine.md#4-추천과-한계-표시)) |

- **속성 이름:** enum이라 정의에 없는 속성은 나올 수 없다.
- **값:** 코드에서 정의와 대조하고, 맞지 않으면 버린다([`validate_constraints`](../backend/app/services/extractor.py "sym:py:app.services.extractor#validate_constraints")).
- **자유값 속성(brand):** 영문 소문자로 받는다(소니 → `sony`).
- **직접 말한 값과 상황에서 따라 나오는 값:** 둘 다 넣고 구분하지 않는다("학생이라 돈이 없어" → 가장 낮은 가격대, "헬스장에서 쓸" → 운동 용도). 이럴 수도 저럴 수도 있으면 넣지 않는다.
- **장소·환경만으로 기능을 짐작하지 않는다 (2026-10-31, [I-13](issue.md#i-13)):** "지하철에서 들어" → ANC 필요, "운동할 때 써" → 방수 필요처럼 넣지 않고 notes에 상황으로 남긴다. 그 기능을 바란다는 말("시끄러워서 볼륨을 계속 키워", "싹 막히면 좋겠어")이 있을 때만 넣는다. 평가에서 "시끄러운 헬스장" → ANC 필요로 단정해 ANC 없는 정답이 1,453위로 밀린 사례가 있었다. 같은 곳에서 써도 원하는 게 다를 수 있다.
- **과잉 추출 금지:** 결과가 그대로 필터가 되므로, 여러 값에 걸치는 일반 명칭("헤드폰", "헤드셋")만으로는 값을 정하지 않고, 값의 뜻에 정확히 맞을 때만 넣는다.
- **확신도를 없앤 이유 (2026-10-31):** 돌려 묻는 질문의 답은 대부분 상황이라 거의 다 "추정 0.7"이 되어, 조건 위반 상품을 거르지 못하고 확신 종료도 나오지 않았다. 확신도 자체도 보정되지 않은 값이었다([roadmap Phase 3+](roadmap.md#phase-3-기능-고도화-암묵적-선호-추론과-추천-보정)).
- **상관없음:** 단어가 아니라 뜻으로 판단한다("둘 다 괜찮아", "그건 신경 안 써"). "모르겠다"는 상관없음이 아니다.

### 구조를 바꾼 이유
- **처음 버전(속성마다 칸):** 모델이 말하지 않은 속성까지 `dont_care`로 채웠다. "언급한 조건만 담는 목록"으로 바꿔 해결했다.
- **호출 하나 → 둘 (2026-10-31):** 질문과 무관한 말이나 돌려 물은 질문의 답에서도 속성을 빠짐없이 찾고 메모리에 남기기 위해, 속성 추출을 별도 호출로 뗐다. 요청 분류 지시는 "맥락이 있어도 발화 자체로 분류"를 지켜야 해서 함께 두지 않았다.

## 3. 평가

[eval_parser.py](../backend/scripts/eval_parser.py)가 [parser_cases.yaml](../backend/evaluation/parser_cases.yaml) 56개 케이스를 실제 API로 채점한다(두 호출을 합친 결과).
- **케이스 구성:** 명시 조건 여러 개, 가격 환산, 상황에서 따라 나오는 값, 부정·상관없음, 짧은 답, 정정, 다른 상품, 잡담, 위험 요청, 맥락이 있는 대화, 돌려 물은 질문에 대한 답·질문과 무관한 말(8개, 2026-10-31 추가), 장소만 말한 답·장면 속 바람을 물은 질문의 답·직접 물은 예산(2026-10-31 추가)
- **통과 조건:** 요청 분류가 맞고, 기대한 값(`expect`)이 모두 있으며, `expect`·`optional`·`allow` 밖의 값이 없어야 한다. 추출 결과가 그대로 조건이 되므로 과잉 추출은 오답이다.

```bash
cd backend
uv run python scripts/eval_parser.py --configs gpt-5-mini:low gpt-5-nano:low --verbose
```

- 55/56의 실패는 맥락이 있는 위험 요청에서 메모리의 값을 다시 뽑은 것이다(분류는 `unsafe`로 맞아 조건에 반영되지 않음). 실행마다 다른 케이스가 하나씩 흔들린다.
- 남은 실패: "사격장에서 쓸 헤드폰"에서 `form_factor=over_ear`, `use_case=general`을 뽑음. 위험 단어 분류용 케이스라 이 문장에 맞춘 지시는 넣지 않았다(흔들림).
- 확신도 없는 버전은 채점이 더 엄격하다(예전에는 추정 값이 기대 밖이어도 오답이 아니었다). optional 맞힘이 준 것은 "지하철 출퇴근 → 무선"처럼 분명하지 않은 값을 이제 넣지 않기 때문이다.

## 4. 대화 메모리

[`ConversationMemory`](../backend/app/services/memory.py "sym:py:app.services.memory#ConversationMemory")는 대화에서 알아낸 사실의 **유일한 기록**이다. 세션 상태(`ChatState.memory`)에 저장된다.

| 항목 | 내용 | 채우는 곳 |
|---|---|---|
| `facts` | 속성 값 기록 `{attribute, value, quote(근거 발화), turn, source: said\|button}`. 같은 속성은 마지막 기록이 이긴다(정정). 같은 값은 다시 남기지 않는다 | 속성 추출 결과, 버튼 답 |
| `notes` | 속성 밖의 사용 맥락. 중복 없이 최대 10개 | 속성 추출의 `notes` |
| `keywords` | 상품 설명 검색용 영어 키워드. 중복 없이 최대 40개 | 속성 추출의 `keywords` |

- **읽는 곳:** 다음 턴의 파서 입력(메모리 요약)과 질문 작성기 입력(메모리 요약), 추천 때 동률 정렬의 텍스트 관련도 질의([`search_text`](../backend/app/services/memory.py "sym:py:app.services.memory#ConversationMemory.search_text"): 근거 발화 + 맥락 + 키워드). 조건이 아닌 속성(주 용도)의 값도 여기 남아 동률 정렬에 쓰인다. 최근 대화는 메모리에 두지 않고 `messages` 테이블에서 8개를 읽어 질문 작성기에 넘긴다.
- **엔진과의 관계:** 엔진이 쓰는 [`PreferenceState`](../backend/app/core/model.py "docid:core.preference-state")는 저장하지 않고 매 턴 메모리(속성별 마지막 값)와 질문 기록에서 만든다([`ChatState.preference`](../backend/app/services/state.py "docid:chat.preference-of")). 그래서 같은 사실이 두 곳에서 어긋나지 않는다.
- **Developer Panel:** 메모리(턴, 값, 근거 발화, 버튼 여부, 맥락)와 질문 기록(시도 횟수, 상태)을 보여준다.

## 5. 질문 작성기 (친구 페르소나)

[`write_question`](../backend/app/services/questioner.py "docid:chat.write-question")은 엔진이 고른 속성 하나를, 그 물건을 잘 아는 친한 친구의 반말로 묻는다.
예: "노이즈 캔슬링이 필요하신가요?" 대신 "지하철 탈 때 음악 볼륨 엄청 올려서 듣는 편이야?"

**메시지 구성: 반응(결론) + 다음 질문**
- 방금 알게 된 것이 있으면 친구가 내린 결론처럼 말하고 바로 다음 질문으로 넘어간다. 확인("맞지?")을 따로 묻지 않는다. 틀렸으면 사용자가 정정하고, 정정은 메모리의 마지막 값으로 바로 반영된다.
- 실제 출력: "그럼 지하철에서 소음 거의 차단되는 게 좋겠네, ANC가 필요하겠어. 혹시 평소엔 주머니에 쏙 넣어다니는 작은 걸 원해, 아니면 귀를 통째로 덮는 큰 걸로 써도 괜찮아?"
- 결론에는 알게 된 값이 분명히 드러나야 한다("편한 걸 원하겠네"처럼 흐리게 말하지 않는다). 결론에는 흔한 일상어·줄임말(노캔 등)을 써도 되지만, 질문 부분에서는 기능 이름을 꺼내지 않는다.

**시스템 프롬프트 설계** ([`build_instructions`](../backend/app/services/questioner.py "docid:chat.question-persona"))
- **돌려 묻는 질문을 미리 정하지 않는다.** 속성별 요령이나 예시 질문을 YAML·프롬프트에 두지 않는다. 대신 방법을 준다.
  1. 그 속성 값에 따라 달라지는 생활 장면(어디서·언제·누구와·무엇을 하면서, 몸·습관, 겪은 불편)을 떠올린다.
  2. 지금까지의 대화와 가장 자연스럽게 이어지는 장면 하나를 고른다.
  3. 장소·환경만 묻고 끝내지 않고, 그 장면에서 친구가 무엇을 바라는지·무엇이 불편한지를 묻는다(같은 곳에서 써도 원하는 게 다르다). 예: "헬스장에서 운동할 땐 트레이너 말이나 주변 소리도 들어야 해, 아니면 음악만 듣고 외부 소리는 막고 싶어?"
  4. 답을 들으면 값이 바로 갈리는 질문인지 확인한다. 연결이 약하면 다른 질문을 고른다.
  5. 질문에서는 기능 이름·전문 용어·보기 이름을 꺼내지 않고, 예를 나열하지 않는다.
- **먼저 계획, 다음 말:** 구조화 출력 `{approach, text}`로 받는다. `approach`에 "장면: …; 답 → 값, 답 → 값"을 한 줄로 적게 해, 답이 값으로 이어지는지 스스로 점검하게 한다(생각할 자리를 출력에 둔다). `approach`는 Developer Panel에만 보인다.
- **다른 상품 예시:** 방법 예시는 러닝화·커피 머신으로만 든다. 헤드폰 예시를 주면 질문이 그 예시로 굳기 때문이다(테스트로 프롬프트에 속성 이름이 없는지 확인).
- **지킬 것:** 정해진 속성 하나만, 반응 한마디 + 질문 하나(80자 안팎), 이미 한 반응·예전 결론 되풀이 금지, 이미 아는 것 다시 묻지 않기, 상품·가격·사실 지어내지 않기, 잡담·유행 질문에는 지어내 답하지 않고 "추천할 때 같이 보여 줄게" 정도로 받기.
- **다시 묻기:** 돌려 물어 답이 안 나온 속성을 다시 물을 때는 쉬운 말로 직접, 둘 중 고르기 쉽게 묻는다(용어 대신 그 기능이 해 주는 일로).
- **직접 묻기 (2026-10-31):** 카테고리 정의에서 `ask_directly: true`인 속성(헤드폰은 가격대)은 돌려 묻지 않고 어림 금액으로 바로 묻는다(한국어는 원화, 영어는 달러). 예: "예산은 대충 얼마 생각해? 3만 원 안, 3만~8만 원, 아니면 8만 원 이상?", "Budget-wise, are you thinking under $20, $20–60, or $60+?" 돌려 물은 예산 질문("막 써, 아니면 오래 쓰려고 챙겨 써?")은 답이 가격대로 이어지지 않아 `$60 이상`으로 잘못 추출되거나 질문을 낭비했다([I-13](issue.md#i-13)).
- **반응에서 짐작 금지:** 방금 알게 된 것만 결론으로 말한다. 거기서 다른 기능의 필요를 덧붙이거나("그럼 방수도 필수겠다"), 지금 물을 속성의 답을 미리 짐작해 말하지 않는다.

**입력:** 알아낼 속성(라벨, 가능한 값), 답할 언어, 상황(첫 턴, 직접 묻기, 다시 묻기, 알아들은 것 없음), 메모리 요약, 최근 대화, 방금 알게 된 것, 방금 한 말.
- **답할 언어:** 사용자 발화의 언어로 쓴다. 영어면 같은 친구 말투의 구어체 영어(예시 하나를 영어로 둠).

**모델과 추론 강도** (같은 5턴 대화로 비교, 2026-10-31, [I-12](issue.md#i-12))

| 설정 | 한 턴 응답 | 결과 |
|---|---|---|
| **`gpt-5-mini` + `low` (기본값)** | 10~14초 | "그럼 ~가 좋겠네. 혹시 …?" 패턴을 지킴 |
| `gpt-5-mini` + `minimal` | 5~9초 | 결론을 흐리게 말함, 잡담에 지어내 답함 |
| `gpt-4.1-mini`, `gpt-4o-mini` (비추론) | 5~8초 | 예산을 직접 묻고 결론을 말하지 않음 |

- 해석 2회(동시)만 약 4초라, 질문 작성 모델을 바꿔도 전체가 크게 줄지 않는다.
- 설정: `OPENAI_QUESTION_MODEL`(비우면 `OPENAI_MODEL`), `OPENAI_QUESTION_REASONING_EFFORT`(기본 `low`).

**실패하면:** YAML의 `question`(영어 사용자는 `question_en`, 직접 묻는 친구 말투 고정 질문)을 쓴다(`debug.question_source = template`). 보기 버튼은 어느 경우든 함께 보내고, 돌려 묻는 문장과 보기가 달라 보일 수 있어 UI는 보기 앞에 속성 이름을 붙인다.

**말투 통일:** 추천 안내, 한계 문장, 거절 문구 등 고정 문구도 같은 친구 반말로 바꿨다.

## 6. 질문에 답하지 않은 말

| 상황 | 처리 |
|---|---|
| 질문 대신 다른 조건을 말함 | 그 조건을 반영하고, 대기 질문은 "답 안 함"으로 닫는다. 엔진이 다시 고른다 |
| 알아들은 것이 없음(모호한 말, "요즘 다들 뭐 써?") | 혼내지 않는다("보기에서 고르라" 하지 않음). 질문을 "답 안 함"으로 닫고, 엔진이 같은 속성을 고르면 질문 작성기가 "다시 묻기"로 더 직접 묻는다 |
| 잡담(`off_topic`, 질문 단계) | 질문 작성기가 한마디 받고 대화를 이어 간다 |
| 같은 속성에 두 번 답이 안 나옴 (`MAX_ASKS = 2`) | 넘어간다(`skipped`, 다시 묻지 않음, 예산은 씀) |

- 대기 질문의 속성 값이 이번 발화에서 나오면(예: "방송은 들려야지" → ANC 불필요) 답한 것으로 본다.
- 질문 기록([`QuestionRecord`](../backend/app/services/state.py "sym:py:app.services.state#QuestionRecord")): 속성별로 마지막 문장, 시도 횟수, 상태(`pending` / `answered` / `unanswered` / `skipped`)를 둔다.
- LLM이 없을 때는 예전처럼 "잘 못 알아들었어. 아래 보기에서 골라 줄래?"와 함께 같은 질문을 다시 보여준다.

## 7. 해석 결과를 대화 상태에 반영
([`apply_parsed`](../backend/app/services/chat.py "docid:chat.apply-parsed"))

| 출력 | 반영 |
|---|---|
| `constraints` | 메모리에 사실로 기록. 같은 속성의 이전 값을 대체(정정). 엔진에서는 직접 답과 같은 조건(1−ε) |
| `notes` | 메모리에 맥락으로 기록 |
| `exclude_ranks` | 해당 상품을 후보에서 제외(`ChatState.excluded`) |
| `price_order` | 대화 상태에 저장. 조건이 똑같이 맞는 상품 사이를 가격순으로 정렬 |

- **알림:** 질문 작성기가 새로 알게 된 것을 결론처럼 말한다. 고정 문구일 때(추천 직전 포함)는 새로 바뀐 것만 "좋아, 마이크 필요까지 챙길게."로 알린다.

## 8. 요청 분류와 Safety

| request_type | 응답 | 상태 |
|---|---|---|
| `shopping` | 조건 반영 후 질문 또는 추천 | 변경 |
| `unsafe` | "미안, 그건 도와줄 수 없어" 후 대기 중인 질문을 다시 보여준다 | 변경 없음 |
| `other_product` | "지금은 헤드폰·이어폰만 추천할 수 있어" | 변경 없음 |
| `off_topic` | 질문 단계: 질문 작성기가 받고 대화를 이어 감([6절](#6-질문에-답하지-않은-말)). 추천 후·질문 작성기 없음: 서비스 범위 안내 | 변경 없음 |

- **분류 기준:** 요청 분류는 맥락이 아니라 발화 자체로 판단하라고 지시한다. 지시가 없으면 맥락에 끌려 쇼핑으로 분류하는 경우가 있었다.
- **분류가 쇼핑이 아니면** 속성 추출 결과는 버린다.
- **위험 단어가 있는 정상 쇼핑:** "사격장에서 쓸 헤드폰", "총 게임용 헤드셋"은 쇼핑으로 분류한다(평가 세트에 포함).
- **응답 언어 (2026-10-31):** 사용자가 영어로 말하면 질문 작성기·고정 문구·보기·추천 근거를 영어로 보여 준다. 고정 문구는 [responses.py](../backend/app/services/responses.py)에 한국어·영어 두 벌, 속성 이름·보기·대체 질문은 YAML의 `*_en`([카테고리 정의](category-spec.md#파일-형식)). 프롬프트(내부 지시)는 한국어 그대로다.
- **요구와 무관한 추천 방지:** 이 Safety 항목은 엔진이 담당한다. 명시 조건을 어기는 상품은 빼고, 모자라면 알린다([IG 엔진 4절](ig-engine.md#4-추천과-한계-표시)).

## 9. 멀티턴 추천 조정

추천을 보여준 뒤에도 대화가 이어진다(`ChatState.finished`는 "추천을 한 번 이상 보여줌"이라는 뜻).
이후 자유 입력은 추천 목록 조정으로 처리하고, 질문 없이 바로 재추천한다([`IGEngine.recommend_now`](../backend/app/core/engine.py "docid:core.engine-recommend-now")).

| 사용자 | 처리 |
|---|---|
| "노캔 있는 걸로", "유선으로 바꿔줘" | 조건 추가·변경 → 재추천 |
| "더 저렴한 걸로" | 조건이 같은 상품 사이를 가격 오름차순으로 정렬. 안내 문구도 "가격이 낮은 순으로 골랐어"로 바뀐다 |
| "1번 말고" | 해당 상품 제외 |
| 조건을 모두 만족하는 상품이 없음 | "일부 조건이 다른 것도 같이 보여 줄게" + 근거에 "(말한 조건과 다름)" |
| 알아들을 수 없음 | "어떤 걸 바꾸고 싶은지 조금만 더 말해 줄래?" |

"더 싼 걸로"를 LLM이 가격대로 바꾸게 하지 않은 이유:
- 현재 추천의 가격대가 섞여 있으면($20, $35, $84) "한 단계 낮은 가격대"가 정해지지 않는다. 실제로 아무 효과가 없었다.
- 그래서 LLM은 방향만 정하고, 정렬은 코드가 결정적으로 한다.

프론트엔드는 추천 아래에 조정 예시 버튼("더 저렴한 걸로", "노이즈 캔슬링 있는 걸로", "1번 말고 다른 걸로")을 보여준다.

## 알려진 한계

- 응답 시간: 자유 입력 한 턴에 10~14초(해석 2회 동시 약 4초 + 질문 작성, 추론 강도 `low`). [I-12](issue.md#i-12)
- 질문 작성기가 가끔 규칙을 어긴다: 첫 질문에서 예를 나열하거나, 예산을 "잃어버리는 편이야?" 같은 연결이 약한 장면으로 묻는다. [I-12](issue.md#i-12)
- 속성 추출의 검색 키워드에 말하지 않은 기능이 섞이고("for the gym" → `sweat resistant`), `over-the-head`를 오버이어로 뽑지 못한다(run 7). [I-13](issue.md#i-13)
- 용어 되묻기("노이즈 캔슬링이 뭔데?")·"일단 목록 보기"·숫자 가격 범위는 아직 처리하지 못한다. 분석과 해결 계획은 [roadmap Phase 3++](roadmap.md#phase-3-대화-견고성-모름되묻기바로-보기숫자-가격)에 있다([I-10](issue.md#i-10)).

## 10. 테스트

- **대화 테스트:** [test_sessions.py](../backend/tests/test_sessions.py)는 가짜 파서·가짜 질문 작성기를 주입해 네트워크 없이 확인한다.
  - 확인 항목: 여러 조건 한 번에, 상황에서 뽑은 값도 조건(조건 위반 상품 제외), 위험·다른 상품 요청, 답 안 한 질문 내려놓기, 추천 후 조건 변경·제외·가격 정렬, 같은 조건 재언급, 메모리(근거 발화·맥락·버튼 답), 질문 작성기 입력과 실패 시 고정 질문, 무관한 말에 다시 묻고 넘어가기, LLM 판정을 규칙으로 덮어쓰지 않기, 영어 발화에 영어 문구·보기
- **동률 정렬 테스트:** [test_relevance.py](../backend/tests/test_relevance.py). 주 용도가 엔진 조건이 아님, 가격 요청 → 주 용도 → 텍스트 관련도 → 평점 순서, BM25·임베딩 RRF, 임베딩 실패 시 BM25만, 질문 단계에서는 임베딩을 부르지 않음.
- **대화 상태 테스트:** [test_state.py](../backend/tests/test_state.py). 메모리에서 엔진 입력 만들기(정정·상관없음·제외), 질문 기록 생명주기(답 안 함 → 다시 묻기 → 넘어감), 저장 왕복.
- **파서·질문 작성기 단위 테스트:** [test_parser.py](../backend/tests/test_parser.py). 두 호출이 실제로 동시에 나가는지(barrier), 결과 합치기, 프롬프트 입력, 실패 처리, 페르소나 프롬프트에 속성 이름이 없는지.
- **실제 LLM을 막는 장치:** `.env`에 키가 있어도 테스트는 실제 LLM을 부르지 않는다. `get_parser`, `get_question_writer`, `get_embedder` 의존성을 테스트에서 덮어쓴다.
- **해석 품질:** 실제 API 평가는 3절의 평가 스크립트로 따로 돌린다. 질문 작성 품질은 아직 자동 평가가 없다(실제 대화로 확인).
