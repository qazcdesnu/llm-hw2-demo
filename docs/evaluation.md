# 평가

← [CLAUDE.md](../CLAUDE.md) · 관련: [roadmap Phase 4](roadmap.md#phase-4-정량-평가) · [architecture](architecture.md) · [LLM 파서](llm-parser.md)

우리 대화 추천 시스템을 비교군과 함께 평가한다. 두 가지 방식이 있고, 둘 다 Developer Panel의 **평가 모드**에서 쓴다.

| 방식 | 사용자 | 정답 | 채점 |
|---|---|---|---|
| 매뉴얼 평가 | 사람이 C4 시나리오를 연기 | 실제 구매 상품 | 정답 순위 자동 + 사람이 자연스러움·만족도 1~5 |
| 자동 평가 | 가상 사용자(LLM)가 시나리오대로 대화 | 실제 구매 상품 | 정답 적중 자동 + LLM 심판(적합·자연스러움·효율 1~5) |

## 1. 시나리오: Amazon-C4

[Amazon-C4](../README.md#평가-데이터-amazon-c4-선택)는 실제 5점 리뷰를 1인칭 요구 문장으로 바꿔 쓴 질의와, 그 리뷰의 상품(실제 구매 상품)의 쌍이다.
[build_scenarios.py](../backend/scripts/build_scenarios.py)가 아래 조건을 만족하는 질의 중 일부를 seed로 뽑아 시나리오를 만든다([`generate_scenario`](../backend/app/evaluation/scenarios.py "sym:py:app.evaluation.scenarios#generate_scenario")).

**C4 질의 고르는 조건** ([`c4_candidates`](../backend/app/evaluation/scenarios.py "docid:eval.c4-candidates"))

| 조건 | 이유 | 남는 질의 |
|---|---|---|
| 정답 상품이 카탈로그에 있음 | 정답 순위를 매기려면 | 126개 |
| 긍정 리뷰 (평점 5, `--min-rating`) | 만족한 구매여야 그 상품이 이 사람의 정답이 된다 | 126개 (C4는 원래 5점 리뷰로만 만들어져 전부 통과. 다른 데이터에 대비해 명시) |
| 리뷰 300자 이상 (`--min-review-chars`, HTML 줄바꿈 제외) | 짧은 리뷰("Dad loves them…")에는 상황·선호 정보가 거의 없다 | **44개** |

- 후보 126개의 리뷰 길이: 최소 102자, 중앙값 234자, 상위 25% 382자. 200자면 79개, 400자면 31개가 남는다.
- 처음 10개(조건 없이 뽑음, 2026-10-31 run 1·2)는 6개가 300자 미만이라 다시 만들었다.

| 필드 | 내용 |
|---|---|
| `persona` | 숨겨진 선호 4~7문장 (영어). C4 질의·리뷰와 **정답 상품의 속성**으로 LLM이 쓴다. 기능뿐 아니라 언제·어디서·어떻게 쓰는지, 무엇이 불편한지 같은 생활 맥락을 담는다(챗봇이 생활 장면을 묻기 때문). 브랜드·상품명은 넣지 않는다 |
| `opening` | 첫 마디(영어). 막연하게, 선호는 많아야 하나 |
| `brief` | 사람이 연기할 때 보는 한 줄 상황 |
| `target_id`, `target_attributes` | 정답 상품과 그 속성 (채점용, API로 미리 보여주지 않음) |

- 가상 사용자가 정답 상품의 속성을 알고 답하는 이유: 질문에 일관되게 답해야 시스템 간 비교가 공정하다(IG 평가의 표준 방식). 리뷰만 주면 속성 질문에 "잘 모르겠어"가 많아져 결과 분산이 커진다.
- 가격은 "실제 가격이 들어가는 예산"으로 쓴다(예: $35 → "about $30-40, no more than $50").
- **영어권 사용자 (2026-10-31):** C4 리뷰·상품 정보·실제 구매자가 모두 영어라, 가상 사용자를 영어로 말하는 Amazon 구매자로 바꿨다. 시나리오 생성·가상 사용자·심판·`llm` 비교군의 프롬프트를 모두 영어로 쓰고, 같은 seed로 시나리오 10개(같은 C4 질의)를 다시 만들었다. 챗봇은 사용자 발화의 언어로 답한다([LLM 파서 8절](llm-parser.md#8-요청-분류와-safety)). 한국어 시나리오는 run 1~5에서 썼다.
- 결과: `backend/evaluation/scenarios/<id>.jsonl` (git 포함). 지금은 10개(seed 42, 위 조건). 운동용 무선 이어폰이 가장 많고 재택근무·운전용 헤드셋, 오버이어, 골전도도 있다.

```bash
cd backend
uv run python scripts/download_amazon_c4.py
uv run python scripts/build_scenarios.py headphones --limit 10
```

## 2. 비교하는 시스템

[systems.py](../backend/app/evaluation/systems.py)

| 이름 | 질문 고르기 | 추천 |
|---|---|---|
| `ig` (우리 시스템) | IG 엔진: 기대 정보량 최대 | IG 엔진 Top-3 |
| `random` (비교군) | 같은 시스템에서 다음 질문 속성만 무작위 (`RandomPolicy`, 시나리오별 seed) | IG 엔진 Top-3 |
| `llm` (비교군) | LLM이 자유롭게 대화. 질문 수·순서 제약 없음(최대 5회) | 검색어 → 카탈로그 BM25 상위 30개 → LLM이 3개 선택 ([`LLMSystem`](../backend/app/evaluation/systems.py "docid:eval.llm-baseline")) |

- `ig`와 `random`은 파서, 메모리, 질문 작성기(친구 말투), 추천기가 같고 **질문 선택 정책만** 다르다. IG의 효과만 떼어 본다.
- `llm`은 IG·속성 엔진을 전혀 쓰지 않는 "그냥 대화하다 추천" 방식이다. 정답 순위를 매기려면 카탈로그 안에서 골라야 해서, 추천할 때 검색어를 쓰고 BM25 검색 결과([`CatalogSearch`](../backend/app/catalog/search.py "docid:catalog.search")) 안에서만 고르게 했다.

## 3. 에피소드와 지표

[`run_episode`](../backend/app/evaluation/runner.py "docid:eval.run-episode"): 가상 사용자([`simulated_user`](../backend/app/evaluation/agents.py "docid:eval.simulated-user"))가 첫 마디를 하고, 시스템이 추천할 때까지(최대 8번 응답) 주고받는다. 이어서 [LLM 심판](../backend/app/evaluation/judge.py "docid:eval.judge")이 채점한다.

| 지표 | 뜻 | 계산 |
|---|---|---|
| Hit@1, Hit@3 | 추천 1위 / 3위 안에 실제 구매 상품이 있는가 | 코드 |
| MRR, 정답 순위(중앙값) | 마지막 상태에서 전체 카탈로그(4,628개) 중 정답의 순위 (`ig`, `random`만) | 코드 |
| 속성 일치 | 추천 1위가 정답 상품의 알려진 속성 중 몇 %와 같은가 | 코드 |
| 질문 수 | 추천 전 시스템 응답 수 | 코드 |
| 적합 (fit) | 추천 상품이 숨겨진 선호를 충족하는 정도 1~5 | LLM 심판 |
| 자연스러움, 효율 | 대화 말투·흐름, 불필요하거나 반복된 질문 1~5 | LLM 심판 |

- 4,628개 중 정확히 그 상품을 맞히기는 어렵다. 그래서 정답 순위·속성 일치·심판의 적합 점수를 함께 본다.
- `llm`은 검색 후보 안에 정답이 있었는지(`target_in_candidates`)도 남긴다(검색 단계의 한계를 분리해 보려고).
- 가상 사용자·심판·`llm` 비교군은 `OPENAI_MODEL`(기본 `gpt-5-mini` + `low`)을 쓴다.
- **가상 사용자 규칙:** 물은 것만 1~2문장으로 답한다. 페르소나에 없는 것을 물으면 그 사람의 상황에서 가장 그럴듯하게 답하고, 정말 알 수 없을 때만 "잘 모르겠어"라고 한다(run 3~5에서 "잘 모르겠어"로 질문을 낭비했다). 페르소나에 없는 강한 요구는 지어내지 않는다.
- **텍스트 정렬 효과:** `ig`·`random`은 동률 정렬에서 텍스트 관련도를 뺀 정답 순위도 함께 남긴다(`extra.target_rank_no_text`, 요약의 `median_rank_no_text`·`hit3_no_text`). 같은 대화에서 정렬만 다른 비교다([IG 엔진 4절](ig-engine.md#4-추천과-한계-표시)).

## 4. 실행

**평가 모드 (Developer Panel → 평가 모드)**
- **매뉴얼 평가:** 시나리오를 골라 새 대화를 시작하면 상황(페르소나)이 보인다. "첫 마디 보내기"로 시작하고 그 사람처럼 대화한다. 추천을 받으면 자연스러움·만족도를 매기고 "채점하고 정답 보기"를 누른다. 실제 구매 상품, 정답 순위, Hit@3이 나온다.
- **자동 평가:** 시스템과 시나리오 수를 고르고 "평가 실행"(실제 LLM 호출, 비용 확인 창). 백그라운드로 돌며 진행 상황(끝난 대화 수)과 시스템별 요약표, 에피소드별 대화·심판 코멘트를 볼 수 있다.

**명령줄**
```bash
cd backend
uv run python scripts/run_eval.py headphones --limit 10                 # ig, random, llm
uv run python scripts/run_eval.py headphones --limit 3 --systems ig llm
```
결과는 SQLite(`eval_runs`, `eval_episodes`, 매뉴얼은 `eval_manual`)에 남고 평가 모드에서도 보인다.

**API** ([evaluation.py](../backend/app/api/evaluation.py))

| Method | Path | 설명 |
|---|---|---|
| GET | `/api/eval/scenarios` | 시나리오 (정답 제외) |
| POST | `/api/eval/manual` | `{session_id, scenario_id, naturalness, satisfaction, comment}` → 정답·순위·적중. 추천 전이면 409 |
| GET | `/api/eval/manual` | 매뉴얼 평가 기록 |
| POST | `/api/eval/runs` | `{systems, limit}` → 백그라운드 실행 시작 (202) |
| GET | `/api/eval/runs`, `/api/eval/runs/{id}` | 실행 목록·요약, 에피소드 |

## 5. 결과

**시범 평가 (2026-10-31, run 3, 시나리오 10개 × 3개 시스템, 리뷰 300자 이상 조건)**

| 지표 | ig | random | llm |
|---|---|---|---|
| Hit@1 / Hit@3 | 0 / 0 | 0 / 0 | 0 / 0 |
| MRR | 0.006 | 0.037 | - |
| 정답 순위 (중앙값, 4,628개 중) | 295 | 113 | - |
| 1위 속성 일치 | 0.83 | 0.86 | 0.81 |
| 적합 (심판, 1~5) | 2.0 | 2.4 | 2.6 |
| 자연스러움 (심판) | 3.3 | 3.5 | 3.5 |
| 효율 (심판) | 2.4 | 2.6 | 2.9 |
| 질문 수 | 5.2 | 5.0 | 4.6 |
| 대화 1개 소요 | 80초 | 80초 | 42초 |

run 2(조건 없이 뽑은 이전 시나리오 10개)도 같은 경향이었다: 정답 순위 중앙값 ig 224 / random 69, 적합 ig 2.4 / random 2.7 / llm 3.1.

**해석: 지금은 IG가 비교군보다 나쁘다. 원인은 IG 계산이 아니라 그 앞뒤 단계다** (대화 기록에서 확인)
1. **돌려 물은 예산 질문을 잘못 추출한다.** 질문 작성기가 예산을 "싼 거 자주 바꿀래, 투자해서 오래 쓸래?"로 묻고, 사용자가 "오래 쓸래, 가성비 좋으면 좋아"라고 답하면 가격대 `$60 이상`이 된다(c4-219: 사용자 예산 6만 원 → 정답 1,561위). 추출 결과를 그대로 믿기 때문에 바로 필터가 된다. IG는 가격대를 자주 먼저 고르므로 ig가 이 실패를 더 많이 겪는다.
2. **상황에서 값을 과하게 단정한다.** "운동하면서 쓰고 운전 중에도 써" → 인이어·방수로 단정(정답은 온이어, 3,249위).
3. **돌려 묻는 질문에 "잘 모르겠어"가 많다.** 가상 사용자는 페르소나에 없는 생활 질문("하루에 얼마나 오래 껴?")에 답하지 못해, 질문을 두 번씩 쓰고 넘어간다. 질문 수가 예산(4개)보다 많은 5~7개가 된 이유다.
4. **정답 순위가 동률 순서에 흔들린다.** 조건이 적으면 수백~천여 개가 같은 확률이고 평점순으로 정렬된다. random의 c4-219 4위는 1,210개 동률 속의 우연이다. 시나리오 10개로는 MRR 차이를 믿기 어렵다.
5. **llm 비교군은 검색에서 막힌다.** 10개 모두 BM25 상위 30개 안에 정답이 없었다(`target_in_candidates` 0/10). 대신 대화가 짧고 심판 점수는 가장 높다.
6. 데이터 오류도 섞인다: c4-219 정답 상품의 주 용도가 `gaming`으로 추출돼 있다(실제 업무용, [I-9](issue.md#i-9)).

**①번 개선 후 (2026-10-31, run 5, 같은 시나리오 10개)**

예산은 직접 묻고([`ask_directly`](category-spec.md#파일-형식)), 장소만으로 기능을 짐작하지 않게 추출·질문 지시를 바꿨다([llm-parser.md 2절](llm-parser.md#2-파서), [5절](llm-parser.md#5-질문-작성기-친구-페르소나)).

| 지표 | ig (run 3 → 5) | random (run 3 → 5) | llm (run 3 → 5) |
|---|---|---|---|
| Hit@3 | 0 → 0 | 0 → 0 | 0 → 0 |
| 정답 순위 (중앙값) | 295 → 368 | 113 → 222 | - |
| 1위 속성 일치 | 0.83 → **0.86** | 0.86 → **0.89** | 0.81 → 0.77 |
| 적합 (심판) | 2.0 → **2.7** | 2.4 → 2.6 | 2.6 → 2.5 |
| 자연스러움 (심판) | 3.3 → 3.7 | 3.5 → 4.0 | 3.5 → 3.6 |
| 효율 (심판) | 2.4 → **3.1** | 2.6 → 2.7 | 2.9 → 2.8 |
| 질문 수 | 5.2 → **4.6** | 5.0 → 4.6 | 4.6 → 4.3 |

- **예산 실패는 사라졌다.** ig 대화 10개 모두 예산을 원화 범위로 직접 묻고 맞게 추출했다(c4-219: 1,561위 → 368위). 질문이 줄고 심판의 적합·효율이 올랐다.
- **정답 순위는 나아지지 않았다.** ig와 random이 같은 조건 집합에 이르는 경우가 많고(c4-219 둘 다 368위, c4-1859 둘 다 489위), 그때 순위는 동률 수십~백여 개(47, 150, 186개) 안의 평점 순서로 정해진다. 이제 순위를 정하는 것은 질문 선택이 아니라 동률 안의 순서다 → 다음 개선은 동률을 텍스트 관련도로 나누기.
- run 3과 run 4(같은 시나리오 5개 재실행)에서 같은 시나리오의 정답 순위가 4위 → 332위처럼 흔들렸다. 한 번 실행한 시나리오 10개로는 순위 지표의 시스템 간 차이를 말할 수 없다.
- 남은 실패: 경계가 어림된 금액 범위("3만 원 미만")를 가격대로 옮기지 못해 같은 질문을 다시 하고, 그 답("상관없어")을 예산 무관으로 바꾼 경우가 있었다(c4-6486) → 추출 지시에 "질문이 보여 준 범위는 순서대로 가격대 값" 규칙을 추가. 가상 사용자의 "잘 모르겠어"로 질문을 낭비하는 문제는 남았다.

| 정답 순위 중앙값 | 278 | 311.5 | - |
| 같은 대화, 텍스트 관련도를 뺀 정렬 | 353.5 | 364 | - |
| 1위 속성 일치 | 0.85 | 0.84 | 0.74 |
| 적합 / 자연스러움 / 효율 (심판) | 2.7 / 3.9 / 4.1 | 2.6 / 3.4 / 3.9 | 2.9 / 4.0 / 4.3 |
| 질문 수 | 3.9 | 4.1 | 4.4 |
| 대화 1개 소요 | 65초 | 66초 | 33초 |

- **첫 적중:** c4-219(재택근무용 온이어 헤드셋)에서 ig가 정답을 1위로 추천했다. 이전에는 주 용도(정답은 `gaming`으로 표기)를 조건으로 걸러 1,561위·368위였다.
- **텍스트 관련도는 아직 손해다.** 중앙값은 좋아 보이지만(278 vs 353.5) 같은 대화끼리 비교하면 ig 10개 중 7개, random 10개 중 8개에서 정답 순위가 내려갔다(좋아진 것은 각 2개). 평점순을 완전히 대신해서, 리뷰가 많은 인기 상품이 정답일 가능성(사전 정보)을 버린 것으로 보인다.
- **추출 키워드가 짐작을 섞는다.** "over-the-head Bluetooth headphones for the gym"에서 `sweat resistant`, `secure fit`처럼 말하지 않은 키워드를 넣는다. 같은 발화에서 `over_ear`는 뽑지 못했다(일반 명칭 규칙이 너무 강함). c4-6486은 이어서 "제자리에 붙어 있고 소음을 막아 줬으면"이 인이어로 이어져 2,701위가 됐다.
- 영어 대화는 질문이 줄고(3.9개) 심판 효율이 올랐다(run 5 3.1 → 4.1). 예산은 달러로 바로 묻는다.

**추가 실험: 조건을 필터 대신 점수로만 쓰면? (2026-10-31, LLM 없이 엔진만)**

조건을 만족하는 C4 정답 상품 40개 각각에 대해, 정답의 알려진 속성을 모두 조건으로 주고 순위를 비교했다.
"필터"는 지금 방식(조건을 어긴 상품을 뒤로), "점수만"은 belief 순서 그대로다. ε는 조건 하나의 무게(작을수록 강함)다.

| 조건 | ε | Top-3 같음 | 정답 순위 중앙값 (필터 / 점수만) | 정답이 Top-3 | 정답이 100위 안 |
|---|---|---|---|---|---|
| 모두 맞음 | 0.05 (지금) | 40/40 | 12 / 12 | 5/40 | 37/40 |
| 모두 맞음 | 0.35 | 39/40 | 12 / 12 | 5/40 | 37/40 |
| 하나 틀림 (예산 등) | 0.05 (지금) | 40/40 | 162 / 162 | 0/40 | 13/40 |
| 하나 틀림 | 0.35 | 40/40 | 260 / 254 | 0/40 | 13/40 |

- **필터를 점수로 바꿔도 상위권은 같다.** 조건 하나를 어기면 점수가 20~60배 낮아져, 필터가 없어도 조건을 다 맞춘 상품이 앞선다.
- **조건을 약하게(ε↑) 해도 틀린 조건에서 회복되지 않는다.** 틀린 조건까지 모두 맞춘 상품이 수백 개라, 정답(하나 어김)은 늘 그 뒤다.
- **조건이 모두 맞아도 Hit@3 상한이 낮다(5/40).** 속성 8개로는 같은 조건의 상품이 수십 개씩 남고, 그 안의 순서는 평점이다. 정답을 위로 올리려면 속성 밖의 신호(메모리의 사용 맥락·발화와 상품 설명의 텍스트 유사도 등)로 동률을 나눠야 한다.

다음 할 일은 [I-13](issue.md#i-13)에 정리했다.

## 6. 한계

- 시나리오 10개는 적다. 조건을 만족하는 44개 전부로 늘리면 약 $3~4다.
- 선물용 리뷰("아빠 선물로 샀다")는 구매자와 사용자가 다르다. 페르소나는 사용자 기준으로 써야 하는데 아직 따로 거르지 않는다.
- 가상 사용자와 심판이 같은 모델이다. 심판이 특정 말투를 선호할 수 있다.
- 가상 사용자가 정답 속성을 알고 있어, 실제 사용자보다 답이 일관된다(시스템 간 비교용이지 절대 성능 지표는 아니다).
- 가상 사용자가 정답 상품의 리뷰를 보고 말하므로, 대화와 정답 상품 글의 텍스트 관련도가 실제보다 높게 나올 수 있다(예: "waterproof (IPX5)"처럼 상품 설명의 표현을 그대로 씀).
- 서버의 `--reload`가 코드 변경으로 재시작되면 실행 중이던 백그라운드 평가가 끊긴다(상태가 `running`으로 남음). 긴 평가는 명령줄로 돌린다.
