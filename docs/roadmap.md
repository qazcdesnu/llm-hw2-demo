## 확정된 결정사항
- 스택: Frontend Vite, Backend FastAPI (Streamlit 대신)
- 저장소: SQLite (세션·대화 상태, 상품 DB)
- 데이터: Amazon Reviews 2023 meta 데이터. 20GB 미만이면 원본을 받은 뒤 필요한 상품만 필터링해 새로 저장
- 속성 개수·종류는 데이터 분석 후 결정 (계획서의 4개 속성에 고정하지 않음)
- Safety 범위
  1. 사용자 요구와 무관한 추천을 걸러내기
  2. 위험한 요청(총기류, 마약류 등)을 감지하고 거부하기
- 대화 방식 (2026-10-31): 속성 추출을 요청 분류와 별도의 LLM 호출로 두고, 알아낸 속성 값·근거·맥락을 대화 메모리에 저장한다. 질문은 친한 친구 페르소나로 생활 장면을 물어 은근히 묻는다
  - 돌려 묻는 질문은 미리 정해 두지 않는다. 시스템 프롬프트가 방법만 알려 주고 모델이 대화에 맞춰 고른다
  - LLM이 있으면 의미 판정(상관없음 포함)은 LLM만 한다. 단어 목록 같은 규칙으로 판정하거나 덮어쓰지 않는다
  - 속성 추출 결과는 그대로 믿는다. LLM 확신도와 "추정" 구분을 없앴다. 알게 된 것은 질문 작성기가 "그럼 ~가 좋겠네. 혹시 …?"처럼 결론으로 말하고 확인을 따로 묻지 않는다
  - 사실은 대화 메모리 한 곳에만 기록하고, 엔진 입력은 매 턴 메모리에서 만든다

## Phase 3+. 기능 고도화: 암묵적 선호 추론과 추천 보정
사용자가 속성을 직접 말하지 않아도, 맥락("통학할 때 쓸 거야", "헬스장에서")에서 LLM이 유용할 속성을 알아내 추천에 반영한다.

**현재 설계 (2026-10-31 변경): 속성 추출 결과를 그대로 믿는다**
- 속성 추출기는 값이 분명히 따라 나올 때만 값을 낸다("지하철 통학용" → anc=yes). 낸 값은 직접 말한 조건과 같다.
- LLM 확신도, explicit/inferred 구분, 확신도 구간(0.85 / 0.5)을 없앴다.
- 알게 된 것은 질문 작성기가 결론처럼 말한다("그럼 시끄러운 소리 막아 주는 게 좋겠네. 혹시 …?"). 확인 질문을 따로 하지 않고, 틀렸으면 사용자가 정정한다.
- 결정 이유
  - 돌려 묻는 질문을 쓰면서 답이 대부분 "상황"이 되었다. 확신도 구간을 그대로 두면 대부분 약한 증거(0.7)가 되어 조건 위반 상품을 거르지 못하고, 확신 종료도 거의 나오지 않았다(실제 대화: 질문 5번 뒤 명시 2개, 추정 4개).
  - 확신도 값 자체도 보정되지 않은 LLM 출력이라, 임계값에 기대는 처리가 근거가 약했다.

**이전 설계 (2026-10-26 ~ 10-31, 기록용)**
- 추정 선호를 확신도 c만큼만 반영하는 약한 증거로 belief에 곱했다(값이 v인 상품 × c, 다른 값 × (1−c)/(k−1)).
- 확신도 ≥ 0.85는 명시로 승격, 0.5~0.85는 약한 증거, < 0.5는 버림. 추정 조건으로는 추천에서 빼지 않았다.
- 드문 값을 추정하면 그 속성의 IG가 올라 확인 질문이 앞서는 효과가 있었다.

**할 일**

- [x] 정정: 같은 속성을 다시 말하면 메모리의 마지막 값이 이기고 belief를 처음부터 다시 계산
- [x] 알게 된 것을 결론처럼 말하고 다음 질문으로 넘어가기 (질문 작성기)
- [ ] 평가
  - 시뮬레이터에 "맥락 발화" 추가: 숨겨진 선호와 함께, 속성을 직접 말하지 않는 상황 설명 문장을 생성
  - 직접 질문 vs 돌려 묻는 질문: 같은 질문 예산에서 Hit@k, Turn-AUC, 조건 충족률

## Phase 3++. 대화 견고성: 모름·되묻기·바로 보기·숫자 가격
사용자가 조건을 모르거나, 용어를 되묻거나, 일단 목록부터 보고 싶어 할 때도 막히지 않고 추천까지 가야 한다 ([I-10](issue.md#i-10)).

**실패 사례 (2026-10-26, 실제 대화)**
```
사용자: 30달러 미만으로 추천해줘. 일단 다른 옵션은 내가 잘 모르겠으니 일단 목록 볼래
봇:     반영했어요: 가격대 $20~60.            ← ① $30 미만인데 $20~60, ② 목록 요청 무시
        노이즈 캔슬링 기능이 필요하신가요?
사용자: 잘 몰라
봇:     잘 이해하지 못했어요. 아래 보기에서 골라 주세요.   ← ③ '모름'을 처리 못 하고 같은 질문 반복
사용자: 노이즈 캔슬링이 뭔데
봇:     지금은 헤드폰·이어폰만 추천할 수 있어요.          ← ④ 용어 질문을 '다른 상품'으로 오분류
        노이즈 캔슬링 기능이 필요하신가요?               ← ③ 또 같은 질문
```

**원인 분석**

| # | 증상 | 원인 |
|---|---|---|
| ① | "$30 미만" → $20~60 | 가격을 구간(low/mid/high)으로만 표현한다. 경계($20, $60)와 다른 숫자 범위를 담을 수 없어 가장 가까운 구간 하나로 뭉갰다. 사용자에게 다른 조건을 반영했다고 알린 셈이라 신뢰 문제도 있다 |
| ② | "일단 목록 볼래" 무시 | 파서 출력에 "지금 결과 보기" 같은 대화 행위가 없다. 엔진은 예산이 남으면 계속 묻는다 |
| ③ | "잘 몰라"에 같은 질문 반복 | "모름"을 담을 출력이 없다. 조건이 0개로 해석되어 문자열 매칭으로 넘어가고, 실패하면 무한히 다시 묻는다. 탈출 규칙이 없다 |
| ④ | "노캔이 뭔데" → 다른 상품 | 요청 분류에 "속성에 대한 질문" 칸이 없어 가장 가까운 `other_product`를 골랐다. 속성 설명 데이터도 없다 |
| 공통 | 평가 세트가 놓침 | 42개 케이스는 모두 "조건을 아는 사용자"다. 모름·되묻기·건너뛰기·숫자 범위 케이스와 여러 턴 시나리오가 없다 |

**해결 방안**

1. **파서에 대화 행위(dialog act) 추가.** 요청 분류(Safety용)와 별개로 아래 중 하나를 출력한다.

   | act | 예 | 처리 |
   |---|---|---|
   | `answer` | "무선이요", "30달러 미만" | 지금처럼 조건 반영 |
   | `dont_know` | "잘 몰라", "글쎄요" | 대기 중인 질문을 상관없음으로 처리. "괜찮아요, 그건 넘어갈게요"라고 안내하고 다음 질문으로 간다 |
   | `ask_about_attribute` | "노이즈 캔슬링이 뭔데?", "IPX가 뭐야" | 속성 설명과 "이런 분께 필요해요"를 보여주고 같은 질문을 다시 묻는다. 질문 예산은 쓰지 않는다 |
   | `show_results` | "일단 목록 볼래", "그냥 추천해 줘" | 질문을 멈추고 지금 조건으로 바로 추천한다(reason `user_requested`). 추천 후 조정으로 이어진다 |

   한 발화에 여러 개가 섞일 수 있다(①+②). 그래서 조건과 act를 함께 반영한다. `show_results`면 조건을 반영한 뒤 바로 추천한다.
2. **속성 설명을 카테고리 정의에 추가.** YAML 속성에 `help`(무엇인지, 어떤 상황에 필요한지)를 넣는다. 설명은 LLM이 지어내지 않고 정의된 문구를 쓴다. 문구가 없을 때만 LLM이 짧게 생성하는 방안은 검토한다.
3. **숫자 범위 조건.** 파서가 `price_min`/`price_max`(USD, 원화는 환산)를 출력한다. 엔진은 실제 가격으로 가능도를 계산한다.
   - 가능도: 범위 안이면 c, 밖이면 1−c, 가격 없으면 중립
   - 구간 속성(`price_band`)은 질문 보기용으로 남긴다
   - 범위 조건이 있으면 구간 질문은 하지 않는다
   - 안내 문구에는 사용자가 말한 범위를 그대로 쓴다("$30 미만")
   - 카테고리 정의에 `numeric` 속성 종류를 추가해 다른 카테고리에서도 쓰게 한다
4. **반복 방지 규칙.** 같은 질문에서 이해 실패가 2번이면 자동으로 상관없음 처리하고 넘어간다. 엔진의 질문 예산과 별개로 "연속 실패 횟수"를 상태에 둔다.
   - 2026-10-31 일부 반영: 답이 안 나오면 혼내지 않고 한 번 더(더 직접적으로) 묻고, 두 번째에는 "물은 것"으로 두고 넘어간다(`QuestionRecord`, [llm-parser.md 6절](llm-parser.md#6-질문에-답하지-않은-말)). LLM이 판정하지 않은 값을 넣지 않으려고 상관없음으로 처리하지는 않는다.
5. **UI 탈출구.** 질문 보기 옆에 "잘 모르겠어요"(= `dont_know`)와 "바로 추천 보기"(= `show_results`) 버튼을 항상 둔다. 질문 옆에는 ⓘ 설명(`help`)을 둔다. 버튼 경로는 LLM 없이 동작한다.
